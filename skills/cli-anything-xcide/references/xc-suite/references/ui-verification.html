ui-verification — XCGUI/WmUi 真实渲染与交互验收

本页由本地 Markdown 生成；样式内嵌，无网络、MCP 或浏览器脚本依赖。

适用：修改纯 XML 界面、WmUi 样式、radio/check 状态、内嵌 UI_ZIP，或需要用截图证明页面可见和可操作时。资源加载与真实构建细节分别见 wmui-styles.md §5.4、module-packaging.md §13。

1. 证据层级

静态 XML、资源登记、控件句柄和适配器计数只能证明声明或模型状态；它们不能证明像素已经绘出，也不能证明鼠标事件命中。验收报告把下列层级分开记录：

  1. 静态层：XML 语法、name/绑定唯一性、页面和列布局、CSS 选择器、resource.res 注册与 UI_ZIP 条目。
  2. 渲染层：当前构建 EXE 的真实窗口截图、客户端矩形、DPI、标题或页面静态区域、唯一选中状态和实际绘制边界。
  3. 事件层：真实鼠标点击、按钮状态、页面互斥显示、保存/还原和窗口退出；每项单独计数。
  4. 外部目标层：真实游戏或其他外部程序。没有执行就标为未实测，不能用私有 fixture 或截图替代。

PrintWindow 返回成功、WaitForInputIdle 返回以及截图工具执行成功，只表示调用或进程阶段完成，不表示窗口已经绘制。首帧可能是全黑或尚未完成的中间帧。

2. WmUi 复选框的绘制范围

layout.width=24 与 layout.height=24 只改变控件盒子，不保证 bkInfoM 宏里的勾选图形没有越界。六态按钮_勾选是带文字按钮样式；若其宏按 20px 控件设计，绘制区可能从 x=5 延伸到 x=25，在 24px 盒子右侧裁切。

修复顺序：

  1. 读取实际 CSS 选择器的 bkInfoM，确认它指向的宏和 98: 状态映射。
  2. 复制现有宏建立工程专用紧凑样式，调整绘制区到控件内部（本次实测为 x=2..22）。保留状态映射、颜色、字体和禁用态，不手写一套缺状态的简化宏。
  3. 修改 CSS 选择器使其实际引用新宏；只复制宏文件而不改 CSS 引用不生效。
  4. 用当前 EXE 的截图或像素工具检查全部实例的真实 bbox。控件尺寸、宏文本和资源存在都不能代替像素结果。

本次 96-DPI 样本的 150 个框均为 [2,2,22,22]；该数值是该构建和 DPI 的证据，不是其他主题、缩放或字体环境的通用阈值。

3. 同组 radio 的运行时状态

XML 中的 check=true 可作为初始值，但运行时同步可能覆盖它。对同一个 groupID 的多个 radio，不要在一个循环里先把目标设为真、再把其他成员逐个设为假；本次实测的 XCGUI 行为中，后续 false 会清掉组内先前的 true。

稳定顺序是：

  1. 遍历同组成员，全部 SetCheck(false)。
  2. 循环结束后只对目标成员 SetCheck(true)。
  3. 更新页面显示和当前索引。
  4. 重新绘制后检查实际唯一选中状态。

这是一条针对已实测运行时行为的同步规则；若更换 XCGUI 版本，应重新做同组对照，而不能把一次工程观察扩展成所有版本的无条件定律。

点击坐标返回成功或目标文件名是 page3 不能证明切到了 page3；必须同时核对页面静态标题和唯一高亮项。

4. 冷启动和多页截图

冷启动检查不发送点击、键盘或热键输入：

  • 启动当前 EXE 后等待第一张非黑且稳定的窗口图；保存等待时间、采样帧数、PID、EXE SHA-256、DPI 和客户端矩形。
  • 只在初始页面的标题和唯一选中 radio 都可见后判定初始渲染完成。
  • 每个页面真实点击，必要时在同一页面重试；截图记录实际点击次数、页面标题是否匹配、selected_navigation 是否恰好包含目标页。
  • 保留首帧黑图作为诊断证据，不把它改名成通过，也不把后续成图反推为第一帧已经绘制。

截图验证覆盖当前 EXE 和当前资源，不沿用旧候选的图片、旧哈希或按文件名推断页面。若只做几何/像素检查，应明确这是 96-DPI 或指定 DPI 的范围，不写成视觉美学或其他 DPI 的通过。

5. 内嵌资源、真实构建和发布包

先判定 UI 是磁盘加载还是内嵌 UI_ZIP：

  • 内嵌模式中，布局、模板、WmUi Base/主题 res、主题 CSS 和字体的改变必须重新构建 EXE。
  • WmUi 运行时按 Base → 主题 res → 主题 CSS 加载；CSS 和字体路径必须相对于 UIZIP 根目录，不能只因设计器 defaultcss 可用就假定运行时已加载。
  • 对内嵌 ZIP 做 CRC、重复条目、条目路径和逐文件字节/SHA-256 比对；至少核对当前四类源文件与实际 PE 资源树。
  • 真实构建记录当前 xcproj、compiled=true、errorCount=0、PE 架构，以及 Debug64/out 产物逐件哈希。静态扫描、旧 EXE、旧报告和 F7 已投递不等价于新构建成功。
  • 便携包只放本次实测需要的 EXE、匹配架构 DLL、启动器和说明；CRC 与逐件字节结果写入报告，不带用户 INI 或测试目录。

6. 输入回归和范围声明

后台输入回归使用唯一类名或 nonce 的私有 Win32 sink，启动前核对目标 HWND 所属 PID、进程路径和前台窗口；不伪装真实游戏类名，不向真实游戏或用户进程投递消息。测试配置写入独立 run 目录，发布目录的用户 INI 前后做存在性和哈希核对。

报告分别写明：

  • 已测：当前 EXE、指定 DPI、私有 sink、实际页面事件和保存/停止等断言。
  • 未测：真实游戏兼容性、其他 DPI/缩放、DirectInput/反作弊路径或任何未执行的外部目标。
  • 证据：当前 EXE SHA-256、测试目录、JSON/截图路径、消息计数和真实退出码。

8. 用 OCR + 真实输入做外部程序联调

历史资料：本节不适用于本仓库要求“不影响前台”的自动化。当前 CLI 用隔离桌面及程序主动接入的测试适配器执行 XCGUI 消息交互；不按本节调用前台激活、光标移动或全局输入 API。只有用户明确要求另一种外部联调流程时，才重新评估其适用性。

适用：被测程序是自绘界面（XCGUI/WmUi，无 UIA/子控件句柄），又要驱动外部目标（真实游戏进程）时。本节数值来自 2026-11-11 一次实机联调（96 DPI、游戏客户区 1244×811、中文 OCR）；换缩放/主题/语言必须重测，不要当跨环境常量。

8.1 整个流程必须在一次命令内跑完

  • 工具调用结束会连同它的作业对象回收子进程：把 GUI 拉起来的调用一返回，窗口句柄立刻失效（实测再取窗口矩形报 WinError 1400 无效的窗口句柄）。启动 → 点击 → 断言 → 收尾写成同一次调用，不要"先启动，下次再点"。
  • 确实需要跨调用时，改用独立后台任务，记录 PID/HWND，每次使用前先 IsWindow 校验，别假设它还在。

8.2 坐标基准只有一种

  • PrintWindow 抓客户区，BitBlt(GetDC(0)) 抓窗口矩形（含边框）。两者原点不同，混用会让所有点击整体偏移。实测用错基准去点「开始」，界面毫无反应，差点被误判成"按钮被禁用"。
  • 每次点击前重新截图，用同一次截图的 origin 换算屏幕坐标；不要缓存上一次的 origin。
  • 窗口会自己动：程序调用 SetWindowPos、焦点切换后重新居中都会改变位置。实测两次采样之间窗口从 (360,130) 漂到左侧，按旧基准点击落到了窗口外。先把窗口 SetWindowPos 钉到固定位置，再开始点。

8.3 前台与所有权校验先于输入

  • SetForegroundWindow 常被前台锁拒绝。可用顺序：AttachThreadInput(当前线程, 前台线程, true) → BringWindowToTop → SetForegroundWindow → 轮询 GetForegroundWindow 确认 → 解除 attach。确认失败就不要发输入。
  • 每次输入前双校验：GetWindowThreadProcessId(目标窗口) 与 WindowFromPoint(落点) 都必须属于本次启动的 PID。实测正是这条拦住了向无关窗口注入点击。
  • 不要用 PostMessage(WM_LBUTTONDOWN/UP) 驱动 XCGUI：实测送达后无反应（页签不切换、开始不生效）。自绘界面要真实鼠标输入（SetCursorPos + mouse_event / SendInput）。

8.4 OCR 定位要先修工具再怪产品

  • 11px 左右的中文直接识别会漏字：放大 2–3 倍再识别能显著改善，但短标签仍会整词丢失（实测「设置」在两个倍率下都没读到）。漏读时先试别的倍率/局部裁剪，再判断产品问题。
  • 识别结果常把单字拆成多个 word：按"同一行 + x 相邻"拼串再比较，不要按整行文本匹配。
  • 建立固定误读映射再归一化：实测「行」被拆成「彳亍」、「未」读成「耒」、「绑定」读成「綁定」、数字间插入全角标点。归一化（去空白、映射、小写）之后断言才稳定。
  • 先用一张自造图（PIL 画已知文字）验证 OCR 通道本身可用，避免把 OCR 的锅算到产品上。
  • 同一标签可能多处命中：实测「刷新截图」同时出现在按钮和提示文案里共 5 个命中。定位必须收敛到唯一命中，多于一个就报错，不要"随便挑一个点"。

8.5 断言只看结果，不看动作成功

  • "点击发送成功""按钮变蓝"都不是证据。要同时证明：目标页正文文字变了 + 导航唯一高亮 + 截图非黑且有方差。
  • 高亮颜色按当次实测取（本次淡蓝 RGB(22,104,220)，未选中 RGB(38,38,38)），不要照搬主题色；换主题或 DPI 重新采样。
  • 外部程序最硬的证据是它自己的日志：绑定、启动、阶段迁移都落盘，比截图和 OCR 更可靠。实测 WaitPanel → ClickStart → VerifyQueue 与界面 Lobby → Queueing 互相印证，才敢说输入真的生效。
  • 报告里必须分开写"产品缺陷"和"测试工具缺陷"：本次两次异常（点「开始」无效、前台获取失败）都是工具侧问题，不能计成产品失败。

8.6 字段为空先回溯依赖链

界面某个字段空白不等于该字段读错。实测「角色名称」为空，同时「周边单位」是 0/0/0——名称来自实体列表逐条取值，列表为空时名称必然为空；而坐标/生命走本地角色指针，仍然正常。先确认上游集合是否为空，再判断偏移或解析是否有问题。

8.7 收尾语义要写清楚

外部程序的「停止」往往只停自己：实测它取消运行令牌、结算计时，不会取消外部程序里的排队/挂起动作。验收报告必须提示人工确认残留状态（例如去游戏面板确认是否仍在队列），否则会留下未预期状态。
